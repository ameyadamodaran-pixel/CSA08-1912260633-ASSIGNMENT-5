## Aim
To convert raw station CSV data and citizen complaints into reliable, cleaned, queryable information; validate cleaning rules; compare implementation methods; and examine lightweight AI features.

## Part A — Design
### A1. Data acquisition
CSV fields are inspected and expected issues identified: missing/invalid values, duplicates, negative values, inconsistent temperature units, malformed data and station-name variation. SQLite tables separate station identity from readings, with an indexed station/date key. Three example questions are answered using parameterized SQL.

### A2. Cleaning and normalisation
The pipeline standardises station/date values, rejects invalid and extreme pollutant readings, converts high Fahrenheit temperatures to Celsius, removes duplicate station/date/hour rows, and fills missing PM2.5 using the median of valid values. Min-max scaling and z-score scaling are discussed and contrasted.

### A3. Visualisation and summary
Line chart for monthly PM2.5 trend; bar chart for station comparison; scatter plot for temperature relationship; and bar/box plot for hourly patterns. Daily summaries use SQL aggregation for minimum, maximum, mean and valid count.

### A4. Debugging and profiling
Print statements and assertions support quick checks; logging provides configurable diagnostics; debugger inspection helps trace variables. `perf_counter`, `timeit` and `cProfile` are planned to measure elapsed time and identify hot functions.

### A5. AI application
A word-list sentiment scorer, frequency-based extractive summariser, and keyword/parameterized-query chatbot are designed. Limitations include small vocabulary, simple negation handling, lack of sarcasm/context understanding and narrow question patterns.

## Part B — Implementation
### B1. Cleaning pipeline
`main.py` reads `messy_air.csv`, validates readings, removes duplicate keys, converts Fahrenheit, imputes missing PM2.5, stores cleaned readings in SQLite, and exports cleaned rows plus rejected rows and SQL summary. A test input deliberately includes quality issues.

### B2. Adversarial data
The implementation uses SQLite parameter placeholders (`?`) rather than concatenating station names into SQL. It also checks required CSV columns and handles empty/malformed or unreadable files, including UTF-8 decoding errors. Test cases include names with apostrophes and SQL-like text.

A simple lexicon sentiment function and sentence-frequency summariser are implemented and tested against complaint examples. A narrow chatbot queries the SQLite database using a station name and PM2.5 intent. The final production decision should be revisited using the benchmark outputs, station data volume, indexing, measured query latency and sentiment agreement on a labelled sample.
